Google's Mobile-First Index Is Done - What That Actually Means for a Bilingual Hebrew-English Site

Short answer: Google officially announced on October 31, 2023 that its move to mobile-first indexing is complete across the web - meaning the engine that ranks your site now checks almost exclusively the mobile version of your pages, not the desktop one, even when someone searches from a desktop computer (source: developers.google.com). If content, internal links, or Schema data that exist on desktop are missing or hidden on mobile - a common failure on bilingual Hebrew-English sites with hamburger menus and alternating RTL/LTR direction - Google simply doesn't see them, no matter how good they look on desktop.

What mobile-first indexing is, and why it isn't just "responsive design"

When Google crawls your site to decide how to rank it, it uses the Googlebot Smartphone crawler in most cases - the version that simulates a mobile phone, not a desktop. Google began this transition back in 2016, and officially completed it for the entire web on October 31, 2023. The implication: whatever that crawler sees when it loads your page on mobile - text, images, links, structured data (Schema) - is what actually enters Google's search index. Content that only exists on your desktop version, however good it is, simply doesn't count.

That's why responsive design - a site that looks good at every screen size - is necessary but not sufficient. A site can look perfect on mobile and still hide entire blocks of content from Google, because someone decided they had no place on a small screen.

Why bilingual (Hebrew-English) sites are especially exposed

Building a site in two languages with alternating text direction (RTL for Hebrew, LTR for English) adds a layer of CSS complexity that a single-language site doesn't have. In practice, we see a few recurring patterns that create a gap between what a human visitor sees and what Googlebot actually crawls:

  • A hamburger menu holding internal links that are visible in the desktop top nav - if they only load on a JavaScript click and don't exist as plain HTML links in the DOM, some crawling tools never reach them.
  • Blocks set to display: none at the mobile breakpoint to "simplify" the page - sometimes including an entire version of content in the other language that disappears when direction flips between RTL and LTR at the wrong breakpoint.
  • Schema data (JSON-LD) injected only in the desktop template of the page, rather than being part of the template shared by both versions.
  • Images with different or missing alt text on the mobile version, when the original image reloads at a different size.

Each of these patterns looks like a minor design detail on its own. In practice, with roughly 62.5% of global website traffic coming from mobile (StatCounter data for Q2 2025, source: statista.com), and Google crawling mainly that version, content that disappears on mobile is content that effectively doesn't exist in Google's eyes - no matter how important it is on desktop.

Four practical checks you can run today

  1. Full content comparison between versions - open the same page on desktop and on an actual mobile device (not just a browser simulation) and verify every paragraph, internal link, and image on one exists on the other.
  2. Check Schema data on both versions - make sure your JSON-LD (BlogPosting, FAQPage, LocalBusiness, etc.) is injected from the shared template, not only from a separate desktop template.
  3. Internal links that don't depend on JavaScript - critical navigation links need to exist as plain <a href> tags in the DOM, not only load on a click action.
  4. Direction (RTL/LTR) checks at every breakpoint - not just on desktop - to catch content that disappears or flips only on mobile.

How to actually check this

The URL Inspection tool in Google Search Console shows exactly how the Googlebot Smartphone crawler sees a given page - the HTML that actually loads, not just what's displayed to a user. Check a few page types (homepage, service page, blog post), not just one, since compatibility gaps tend to cluster in specific templates rather than appear evenly across the whole site.

How this connects to Core Web Vitals

Mobile-first indexing and site speed are two separate topics that meet at one point: both are measured on your site's mobile version, not desktop. A site that's fast on desktop but loads slowly on mobile doesn't just lose visitors - it's also the version Google actually measures and ranks you by.
